QTable использует архитектуру с раздельными репозиториями фронтенда и бэкенда и единой продуктовой моделью:

```text
qtable-web / QTable Web App
React 19 + TypeScript 7 + VTable + Apollo
                 │
      REST / GraphQL / WebSocket / OAuth
                 │
qtable-server / QTable API & Domain Services
FastAPI + Strawberry GraphQL
                 │
      ┌──────────┼──────────┐
      │          │          │
 PostgreSQL    Redis    S3-compatible
                         object storage
```

## Веб-слой: qtable-web

[`QingZoneX/qtable-web`](https://github.com/QingZoneX/qtable-web) отвечает за опыт конечного пользователя, маршрутизацию, отрисовку представлений, совместную работу и интерфейсы ИИ-процессов. Сервер разработки слушает `9100` по умолчанию; прод-образ использует Nginx для SPA, прокси и защитных заголовков.

## Слой сервисов: qtable-server

[`QingZoneX/qtable-server`](https://github.com/QingZoneX/qtable-server) слушает `9000` по умолчанию и отвечает за модель данных, права, автоматизацию, аудит, поиск, вложения, OAuth и ИИ-сервисы. Сервер — конечная доверенная граница прав и правил записи.

## Данные и время выполнения

Стандартный стек самостоятельного хостинга использует PostgreSQL 16, Redis 7 и MinIO или внешнее S3-совместимое объектное хранилище. SQLite — только явный лёгкий откат, а не путь прод-развёртывания по умолчанию.

## Границы безопасности

Все детали, поиск, агрегация Dashboard, доступ к вложениям и контекст ИИ должны проходить проверку прав на сервере. Клиент не может скачивать данные, невидимые текущему пользователю, для анализа или ИИ.
