---
title: Чек-лист production
description: "Реальные проверки при оценке самостоятельного развёртывания QTable v0.1.1-alpha."
---

`v0.1.1-alpha` — это Git-тег открытого предпросмотра. Прежде чем открывать QTable реальным пользователям, выполните проверки ниже в среде, повторяющей топологию production.

## Версия и происхождение

- [ ] `qtable-server` и `qtable-web` используют совместно проверенный тег `v0.1.1-alpha` или более явный точный commit.
- [ ] При Compose из исходников оба репозитория находятся рядом и `QTABLE_UI_CONTEXT=../qtable-web` в `.env`.
- [ ] При готовых образах целевой тег действительно существует в реестре, а digest зафиксирован.
- [ ] Не путать «опубликованный Git-тег» с «опубликованным GitHub Release / стабильным артефактом».

## Конфигурация и секреты

- [ ] `APP_ENV=production`.
- [ ] Сменены `SECRET_KEY` по умолчанию, пароль БД и учётные данные объектного хранилища.
- [ ] Задан стабильный корректный Fernet `ENCRYPTION_KEY`, общий для всех экземпляров.
- [ ] OAuth plain PKCE, динамическая регистрация и отладочный токен сброса выключены.
- [ ] API-ключ провайдера не попадает в переменные фронтенда, поля таблиц или логи.

## Сеть и безопасность браузера

- [ ] Открыт только вход web / reverse proxy; API, PostgreSQL, Redis и админка MinIO остаются в приватной сети или на loopback.
- [ ] Настроены TLS, HTTP → HTTPS и HSTS.
- [ ] CSP, X-Content-Type-Options, Referrer-Policy, защита от фрейминга и Permissions-Policy qtable-web не ослаблены внешним прокси.

## Продуктовый контур

1. Войдите и проверьте права Workspace / объекта / строки.
2. Реально выполните показательные пути чтения/записи в Grid, Kanban, Gantt, Calendar и Gallery.
3. Проверьте агрегацию Dashboard, публичный доступ и поведение доступа после смены прав.
4. Проверьте загрузку/скачивание вложений и отказ после потери прав.
5. Проверьте Recycle Bin Restore / Purge.
6. Проверьте хотя бы одно правило автоматизации и историю выполнения.
7. При включённом ИИ проверьте Preview → Confirm → Apply и повторную проверку прав.
8. Реально выполните резервное копирование и восстановление PostgreSQL + объектное хранилище на непрод-копии.

Runbook резервного копирования, восстановления и обновления продолжает дорабатываться в Alpha. Для прод-развёртывания реальные тренировки восстановления, фиксация версий и проверка отката должны быть условием выхода, а не просто наличием «файлов резервной копии».
